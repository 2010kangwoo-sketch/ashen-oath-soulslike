# Ashen Oath 기반 설계

이 문서는 10차 본작업에 앞서 변경하지 않을 핵심 기술 기준을 정한다.

## 1. 목표

- 설치형 게임 엔진 없이 최신 데스크톱 브라우저에서 실행한다.
- GitHub 저장소의 `main` 브랜치가 항상 배포 가능한 상태를 유지한다.
- 각 차수는 이전 차수 위에 쌓이며, 전투 감각을 우선 검증한다.
- 10차 결과물은 넓기만 한 맵이 아니라 시작, 탐색, 일반 전투, 체크포인트, 보스, 결말이 연결된 짧은 데모다.

## 2. 고정 기술

- Three.js: 렌더링, 카메라, 조명, 모델 및 애니메이션
- TypeScript: 상태와 전투 판정의 타입 안정성
- Rapier 3D compat: 충돌, 강체, 캐릭터 이동 기반
- Vite: 개발 서버와 정적 빌드
- GitHub Actions + Pages: `main` 푸시 자동 검증 및 배포

Rapier compat 패키지는 WebAssembly를 JavaScript에 포함하므로 GitHub Pages의 하위 경로에서도 배포 실패 가능성을 줄인다.

## 3. 설계 원칙

### 전투

- 입력을 즉시 받아들이되, 공격 중 취소 가능한 구간과 불가능한 구간을 명시한다.
- 어려움은 불명확한 판정이 아니라 읽을 수 있는 예고, 거리, 타이밍에서 나온다.
- 구르기 무적 시간과 피격 판정은 애니메이션의 겉모습과 일치시킨다.
- 적은 플레이어를 추적하기만 하지 않고 대기, 견제, 진입, 공격, 회복 상태를 갖는다.

### 공간

- 첫 지역은 거대한 오픈월드 대신 서로 연결된 성역과 폐허로 제한한다.
- 전투 공간에는 회피할 여유가 있어야 하며, 카메라가 벽에 끼지 않아야 한다.
- 계단, 문턱, 좁은 통로에서 캐릭터가 걸리지 않도록 충돌 형상을 시각 메시보다 단순하게 유지한다.
- 체크포인트에서 보스까지의 재도전 동선은 짧고 명확하게 만든다.

### 성능

- 목표 해상도: 1920×1080 데스크톱 브라우저
- 목표 프레임: 일반 노트북에서 45 FPS 이상, 권장 60 FPS
- 픽셀 비율 상한을 두고, 그림자와 후처리는 품질 단계로 조절한다.
- 실제 에셋 도입 전에는 절차적 도형으로 시스템을 먼저 완성한다.

## 4. 현재 빌드가 검증하는 것

- Three.js WebGL 렌더러 생성
- Rapier 키네마틱 캡슐 플레이어 이동
- 계단 자동 오르기, 바닥 스냅, 경사 제한
- 카메라 기준 이동과 장애물 카메라 당김
- 조명, 그림자, 안개, 카메라 동작
- Rapier 3D 비동기 초기화 및 강체 충돌
- 고정 시간 간격 물리 루프
- 화면 크기 변화 대응
- TypeScript 엄격 검사
- GitHub Pages 하위 경로용 상대 asset 빌드
- GitHub Actions 자동 검증 및 배포

Pass 0의 낙하 시험체는 Pass 1에서 플레이어로 교체되었다. `R`을 누르면 플레이어를 시작 지점으로 되돌릴 수 있다.

## 5. 디렉터리 기준

- `src/core`: 게임 생명주기, 루프, 로딩
- `src/physics`: 물리 엔진과 충돌 계층
- `src/world`: 지역, 지형, 배치
- `src/ui`: HUD와 메뉴
- `src/config`: 조절 가능한 수치
- `docs`: 설계 결정과 차수별 검증 기록
- `tools`: 자동 검증 스크립트

향후 `src/player`, `src/combat`, `src/enemies`, `src/camera`, `src/audio`, `src/assets`를 차수에 맞춰 추가한다.

## 6. 금지 사항

- 모든 시스템을 하나의 `main.ts`에 몰아넣지 않는다.
- 임시 수치를 코드 여러 곳에 중복해서 적지 않는다.
- 시각 메시를 그대로 복잡한 충돌 메시로 사용하지 않는다.
- 전투 판정을 프레임 속도에 종속시키지 않는다.
- 출처와 라이선스가 불명확한 모델, 음악, 효과음을 저장소에 넣지 않는다.
- 빌드가 깨진 상태로 다음 차수에 넘어가지 않는다.
